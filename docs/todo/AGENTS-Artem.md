# Repository Guidelines

This file is the single source of rules for AI agents and contributors working with the repository. Keep the instructions concise, verifiable, and aligned with the current state of the project. Only humans may edit this document.

## Project Structure & Module Organization

- `.agents` - developer agent directory.
- `.agents/commands` - Claude slash commands.
- `.agents/idea` - ideas and proposals.
- `.agents/implementation-details` - brief notes on implemented functionality.
- `.agents/prompts` - prompts.
- `.agents/reports` - reports: observations, measurements, defect analyses, and run results.
- `.agents/reports/REPORTS.md` - report index.
- `.agents/review` - reviews.
- `.agents/skills` - skills.
- `.agents/tasks` - tasks.
- `.agents/tasks/TASKS.md` - task registry.
- `.devcontainer` - devcontainer configuration.
- `agent/scripts` - checks and the container entrypoint.
- `agent/data/source` - original project data. Read-only.
- `agent/data/decoded` - original project data with filename encodings corrected.
- `agent/AGENTS.md` - cli agent instructions. Reading and use prohibited.
- `.gihub/workflows` - Automatic launch of GitHub actions and container deployment upon commit.
- `README.md` - project description.
- `agent` - the software solution under development.
- `tmp` - temporary files and logs.
- `docs` - developer documentation.

## Naming Conventions

- **Core naming rules**
- Keep all documentation in the `.agents` directory standardized: use kebab-case, sequential numbering `XXXX` starting from 0001, and filenames that describe their contents as precisely as possible.
- The command, skill, and prompt directories, as well as the task registry, are exceptions.

## Working with tasks

- Add a task entry to the task registry for every separate task.
- Task registry entry format: `- [ ] XXXX-some-task: brief description of the task`.
  - [ ] - active task.
  - [p] - partially completed task.
  - [c] - cancelled task.
  - [x] - completed task.
  - [u] - urgent task.

Tasks may be large and must include exit criteria that split one large task into several smaller items and mark their completion. Whenever possible, mark an item complete immediately after satisfying an `Exit criteria` item. Example:

```markdown
## Exit criteria

- [x] Logs contain no prompts/responses/secrets; correlation ID is present.
- [x] `doctor` does not modify the system; extended checks pass.
- [x] Error taxonomy and exit codes are documented and stable.
- [ ] `close()` does not leave a hung process (bounded timeout).
- [ ] Retry applies only to idempotent startup/status operations; turns are not retried automatically.
- [ ] Tests cover logging (redaction, level, correlation), exit codes,
      doctor checks, retry, and cleanup timeout.
```

## Working with reports

Save all reports, remarks, and observations in the reports directory, then add a brief report description to the registry.

## Documentation

Update documentation alongside the implementation, not after it becomes outdated. For completed functionality, add or update a brief file in `.agents/implementation-details` using the standardized naming convention.

Documentation must be concise, specific, and truthful. If behavior and/or a task is only planned, keep it in the tasks directory; if it is implemented, document its actual behavior and initialization steps.

When working with documentation, one should adhere to the principles of minimalism.

## Agent-Specific Instructions

Respect existing user changes and do not revert unrelated files. When creating new modules, follow the project's scaffold conventions and keep the code minimal.

When completing a task, add a brief completion note to the task documentation.

Maintain a report in `implementation-details` on the progress of the corresponding task from `tasks`.

## RULES

- Reading `.env` and similar sensitive data is prohibited.
- Follow the DRY, KISS, and YAGNI patterns.
- Programming decisions, code comments, git operations, shells, application UIs, and similar artifacts must be written only in English.
- All `AGENTS.md` and `skills` must be written strictly in English.
- Conduct dialogue with the developer in the language he uses to address the agent.
- Before implementing a request to create modules, add project functionality, and so on, check for a corresponding task. If no task exists, first create a new task, plan the implementation, and only then begin implementing it.
- Do not perform tasks without an explicit command to do so.
- Do not modify data files or files generated by Python modules without an explicit command.
- Follow the project's design language and architecture. If they need to be violated, coordinate this with the developer.
- Do not run interactive scenarios that require user input the agent cannot provide (for example, ChatGPT login via `login_chatgpt()`/`login_chatgpt_device_code()` or a blocking `handle.wait()`). Leave such steps to the user and mark them in the task/documentation as "performed manually." Implement and verify using a fake runtime and unit tests without a real account. Run processes that may spawn `codex` only in non-blocking mode with an explicit timeout; do not block the session with an indefinite wait.
- If the rules in these instructions overlap with skill rules, skill rules take precedence.
- Git commands involving the remote repository are prohibited without an explicit command from the developer.
- The `codex` always uses `Ponytail` skills.
- The `codex` must recheck its result after completing the task.
- Comments in code and executable files should be minimalist.
- When executing a task, there's no need to include its number in the code comment, as tasks can be deleted, but the garbage remains. The same applies to other agent-generated documents.
- Agent directories containing tasks, implementation details, reports, and reviews may be subject to periodic cleaning.
- **Compliance with the rules is mandatory at every stage of development.**
